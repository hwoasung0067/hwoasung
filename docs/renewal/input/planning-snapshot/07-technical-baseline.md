## 높은 우선순위 문제와 가설
1. 제품/메뉴 전환: view 상태(setView/navigateTo)로 관리하며 browser URL을 변경하지 않는 것으로 보임. GA4 페이지가 '/'로만 집계되는 문제를 설명할 수 있음.
2. 제품 상세가 selectedProduct 모달: 상세 고유 URL이 없으면 제품별 자연 검색·직접 공유·통계 추적에 한계.
3. 핵심 정보가 Firestore에서 동적으로 로드됨: 봇이 렌더링하는 최종 HTML과 색인 가능 여부 실험 필요.
4. index.html의 OG 대표 URL 일부가 과거 vercel.app과 현재 도메인으로 혼재. 실제 서비스와 비교 점검.
5. SEO 메타 useEffect에 의한 동적 변경이 있어도 독립 URL과 크롤러 확인이 필요함.
6. 프런트엔드에서 관리자 뷰로의 진입은 별도의 라우트라기보다 화면 상태로 처리되는 것으로 보임. 인증·Firestore 규칙·권한/노출 점검 필요(취약하다고 단정하지 않음).
7. 일부 페이지에 무거운 3D iframe(Spline) 등장: 모바일 성능/접근성과 전환 기여 여부 점검.
8. Cloudinary, Tally, Firebase 데이터 보존과 인증/키 관리 규칙이 리뉴얼 변경에 영향을 미침.

## 2026-10-16 기술 영향: ERP 내 온라인 영업문의 관리 (D-026)
- **확정된 업무 목표:** 현재 ERP의 거래처 등록, 작업의뢰서, 원단 송장 발행 흐름을 그대로 활용한다. 별도 CRM·독립 영업 앱은 만들지 않고 ERP 내부에 문의 관리 페이지를 두는 방향.
- 이 홈페이지 저장소에서 ERP 연결/데이터 쓰기 방식은 **아직 기술적으로 검증되지 않음**. 실제 ERP 코드·API·거래처/작지/송장 데이터 구조 및 사용 중인 권한 모델을 확인한 뒤 별도 ERP 구현 설계가 필요하다.
- 신규 문의 데이터는 생산·재고·단가·청구 처리와 분리한다. ERP 작지/송장/거래처를 문의 단계에서 임의 생성하지 않고, 실제 거래 성사 후 기존 ERP ID로 안전하게 참조한다.
- 중복 거래처, 동일 업체 여러 문의, 기존 거래처의 신규 제품 문의, 작업의뢰서와 송장의 여러 건 관계, 취소/재발주/일부 출고 등을 고려해 식별·결합 규칙을 별도 정의.
- 홈페이지→ERP 문의 전달 시 인증·스팸·중복 제출·개인정보 동의/보관·서버 권한 및 오류 재시도 방법 검증. Gmail·네이버 톡톡·카카오비즈니스 자동 수집은 별도 지원 여부 확인 전 보장 불가.
- 단순히 조회·링크했다고 ERP 성과가 자동 확정되는 것이 아니라, ERP의 실제 주문/출고 시점과 구매 전환의 차이를 구분해야 한다.
- 홈페이지/ERP 간 연동은 **양 저장소 각각의 담당 구현과 회귀 테스트를 설계·승인한 다음** 진행한다. `main`/운영 ERP/운영 홈페이지/DB를 지금 변경하지 않는다.

## 2026-10-16 채널별 외부 API 확인 (D-027, 구현 가능성 미확정)
- **홈페이지 문의 폼/메일:** 폼 성공 응답 기반 webhook 또는 전용 이메일 읽기 기반의 ERP 접수 후보. 기존 Tally 운영과 비교, 접근권한·중복제거·원본 참조·재시도·오류가시화를 먼저 설계.
- **네이버 톡톡:** NAVER 공식 chatbot-api(https://github.com/navertalk/chatbot-api)는 챗봇 연결 webhook을 통해 사용자의 send 등 이벤트를 받는다. 다만 현재 일반 상담 계정의 모든 인간 상담 내역/과거 기록을 그대로 읽어올 수 있다는 의미가 아니다. 현 톡톡 설정·챗봇 연동 권한/상담 흐름을 실제 계정에서 테스트하기 전 자동 수집 확약 금지.
- **카카오 일반 비즈니스 채널 1:1:** 개발자 문서(https://developers.kakao.com/docs/ko/kakaotalk-channel/common)에는 채널 추가/채팅방 진입·채널 관리 API 등이 있으나 상담 대화 조회 API는 없다. 카카오 개발자 공식 답변(https://devtalk.kakao.com/t/1-1-api/146646)은 상담톡 공식 딜러 연동 경로를 안내한다. 상담톡 도입은 유료/별도 운영 체계가 될 수 있고 기존 채팅 관리자 사용 방식에 영향을 줄 수 있어 당연히 설치되는 기능이 아니다.
- **전화:** 현재 통화 인프라를 확인하기 전 고객의 통화 내용 자동 기록 가능하다고 가정하지 않는다. 간단한 상담 등록 UX 후보를 고려.
- **설계 후보:** 자동 수집 채널은 채널 ID·원본 이벤트 ID로 중복을 방지하고 수신 실패/지연·재시도·누락 대조 기능을 갖춘 '접수 대기함', 자동 수집 불가 채널은 최소 입력 '빠른 추가'. 두 갈래 모두 ERP만 사용. 미수집 대화를 전부 수집했다고 주장하면 안 됨.
- **확정되지 않은 사항:** 기존 톡톡 챗봇 설정, 카카오 1:1/상담톡 사용 여부, 전화 교환 시스템, API 사용 조건/가격, 개인정보 동의 범위, ERP 백엔드 데이터 모델. 구현은 ERP 저장소 구조 확인·사용자 승인 후.
  
## 2026-10-17 범위 결정: 채널 통합 자동화 보류 (D-028)
- 카카오비즈니스는 **일반 1:1 채팅**을 사용하는 것으로 사용자 확인됨. 상담톡 공식 딜러 연동은 초기 범위에서 제외.
- **초기 요건:** ERP 내부의 선택적 수동 문의 메모 기록 공간. 외부 이메일·톡톡·카카오·전화의 API/webhook 자동 수집, 미수신 대조·재시도, 후속 연락 알림, CRM 단계 파이프라인 등은 **현재 구현 요구사항이 아니다**.
- 사용자가 직접 선택한 중요한 문의만 별도 기록하며 기존 원본 채팅·메일은 그대로 둔다. 모든 문의가 ERP에 등록될 것처럼 가정하거나 '수집률' KPI를 설정하지 않는다.
- 문의 메모는 기존 ERP 거래처·작업의뢰서·송장, 생산·재고·청구 데이터와 안전하게 **논리적·데이터상으로 분리**한다. 상세 스키마/실행 및 테스트는 ERP 저장소 별도 조사·승인을 요한다.
- 문의 빈도 또는 유실이 증가한다면 그때 자동 수집 및 진행 상태 관리의 가치/기술 제약/비용을 재평가한다. D-027의 자동 접수 대기함은 현재 보류 상태.
