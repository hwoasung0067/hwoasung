# 화성섬유 홈페이지 제작 실행 계획 v1
작성: 2026-10-23 KST
상태: AI 권장 실행 계획. 기존 브랜드/5장면/브라우저 시안 승인은 유지하며, 새 상세 디자인·운영 구현·배포 승인을 뜻하지 않는다.
근거: context/current-direction.md, context/design-judgment.md, output/reviews/browser-03.md, 기존 04/06/07/08 기획 문서.

## 목표와 진행 전략
방문자가 실제 원단 제조·공급사임을 즉시 이해하고, 좋은 제조사의 감각을 경험하며, 원하는 원단이나 용도에서 상담으로 이어지게 만든다. 기존 browser-03을 완성안으로 간주하지 않는다.

추천: 대표 구간의 시각 완성도를 먼저 검토한 뒤 홈 전체로 확장하고, 이어 제품 탐색·상담까지 하나의 고객 동선으로 완성한다. 브랜드 재정의·프레임워크 재선정부터 시작하지 않는다. 최종 승인은 화면/자산/동작이 구체적으로 검토 가능한 상태에서 받는다.

## 단계 1 — browser-04 시각 방향을 실제 화면으로 구체화
현재 승인 범위 내 즉시 진행 가능.

- browser-03 소스 보존. browser-04는 별도 버전으로 제작하고 변경 이유/피드백 ID를 기록.
- 먼저 Hero + Our Fabrics + Manufacturing 초입까지 연결되는 PC·모바일 비교물을 제작한다. Hero만 예쁘고 아래와 단절되는 문제를 피한다.
- A(1순위): 밝은 비대칭 편집 안에서 현장 사진과 큰 한글 문구를 한 구도로 결합. 원단 접근 명확, 모바일에서도 사진을 지나치게 아래로 밀지 않음.
- B(좁은 비교안): 같은 내용·사진을 활용하되 사진 비중을 높인 도입. 몰입감은 강하지만 저해상도/소재 부족이 더 드러날 수 있음. 전체 다크 방향으로 바꾸지 않음.
- 두 안은 사진·문구 조건을 같게 하여 구도 차이를 평가. 새 컬러/슬로건 후보를 동시에 대량 증식하지 않음. 전체 홈 두 벌을 먼저 만들지 않음.
- 갤러리는 품목 접근의 동등성을 지키면서 사진 비율/정렬/여백에 변화. 주력 4종+보드레가 모두 명료해야 함.
- 현재 사진으로 레이아웃 검토는 가능하지만 고화질 제조/제품 실사 완성이라고 주장하지 않음. 영상 제작 보류 유지.

산출물: browser-04 A/B 대표 구간, PC·모바일 화면, 추천/단점·미디어 공백·변경 기록.
검토 지점 1: 사용자가 A/B 중 기준 구도와 인상을 평가. 이미 합의한 철학/5장면을 다시 묻지 않음.

## 단계 2 — 다섯 장면 전체를 하나의 리듬으로 완성
- 채택한 대표 구도를 바탕으로 Hero→Fabrics(+사용처)→Manufacturing→Field Notes→Contact 전체 시안을 연결.
- 밝은 도입/소재→깊이 있는 제조 장면→조용한 기록→열린 문의의 밀도 차이 설계.
- 문구는 짧게 편집하되 제품명·공정 구분·다음 행동 유지. 긴 Why/영업 압박·검증 안 된 수치 배제.
- 메뉴/제품 선택/사용처 선택/모달 또는 상세 시안/문의 맥락 이어주기. hover 없이 기본 정보가 보이게 함.
- 의미 있는 포인터 반응·이미지 상세 탐색·절제된 스크롤 진입만 사용. 터치·키보드·reduced-motion 함께 설계.

산출물: browser-04 전체 홈 PC·모바일, 동작 가능한 검토 동선, 화면별 QA/남은 이슈.
검토 지점 2: 홈 전체의 분위기·정보량·리듬을 한 번에 피드백. 픽셀 단위 작업마다 승인 요청하지 않음.

## 단계 1~3과 함께 진행 — 콘텐츠/이미지 증거 확보
- 기존 사진/제품 데이터/Cloudinary 구조를 읽기 범위에서 조사. 실제 상품 사진과 품목명이 맞는지·공개 권한이 확인되는지 기록. 운영 DB 쓰기 없음.
- 꼭 필요한 최소 컷부터: 주력 4종+보드레 대표 실사 5컷, 현장 대표 1컷, 다른 실제 공정/원사·생지 디테일 2~3컷. 이는 수집 목표이며 현재 보유/촬영 약속 아님.
- 보유 자산으로 부족한 부분만 구체적인 촬영 목록으로 제시. 사용자에게 막연히 모든 사진을 새로 달라고 하지 않음.
- 제품 사진이 부족해도 레이아웃은 진행하되, 제품별 시각 최종 승인과 공개 직전에는 품목 매칭/권리/화질 확인 필요.
- 블로그는 기존 실제 글 제목/URL을 바탕으로 바이어 질문별 선별. 이미지가 AI 도식인지 실제 현장인지 구분.

## 단계 3 — 제품 탐색부터 문의까지 상세 경험 설계
아래는 권장 최소 범위이며 상세 IA 확정 전. 기존 04 기획과 실제 제품 스키마에 대조한다.

| 화면/동선 | 필수 역할 | 초기 제외 |
|---|---|---|
| 원단 목록/제품군 | 주력 4종+보드레, 필요한 분류/용도 진입 | 실제 데이터 없는 복잡한 필터 |
| 제품군/검증된 원단 상세 | 실사·확인된 사양·용도 조건·문의 연결 | 허구 SKU·실시간 재고/가격·즉시구매 |
| 사용처 탐색 | 본딩/누빔/PU코팅/담요에서 관련 원단/조건 상담 | 검증 안 된 용도 적합성 보장 |
| 제조·공급/회사 | 실제 거점·자체 편직·협력 가공·공급 설명 | 장황한 기업 자기평가 |
| 인사이트 | 글 선별 목록/외부 블로그 연결 우선 | 필요성 확인 전 별도 CMS 구축 |
| 문의 | 제품/용도/샘플 맥락을 이어 최소 정보로 상담 | ERP·채널 통합 CRM·고객 데이터 자동 수집 |

우선 대표 제품 상세 하나와 문의 화면을 PC·모바일로 이어 붙여 실제 바이어 동선을 검토한다. 사용처/회사를 별도 페이지로 만들지, 공통 화면 내 진입으로 충분한지는 콘텐츠량과 탐색 결과로 제안한다.
문의는 기존 Tally/메일/전화 등 유지·개선안을 실제 운영 경로 확인 후 비교. 검토용 mailto는 운영 문의 접수 구현 완료가 아님.
검토 지점 3: 홈+대표 상세+문의의 디자인/범위/연락 경로를 구체적으로 확인하고 운영 구현 범위를 승인.

## 단계 4 — 승인된 시안을 운영 가능한 프런트엔드로 구현
별도 구현 범위 승인 후 착수. 기존 React/Vite/Firestore/Cloudinary/Tally를 출발점으로 실제 의존성과 운영 배포 구조를 확인한다. 유행을 이유로 프레임워크를 교체하지 않음.

- 기존 제품 데이터/관리자 기능/문의 경로/운영 도메인·자동 배포 연결부터 확인. 새 구조와 기존 항목 매핑표 작성.
- Header·Footer·제품 UI·문의 UI 등 재사용 단위로 분리. 브라우저 시안 코드를 그대로 운영 교체하지 않음.
- 제품/페이지 고유 URL, 직접 진입/새로고침/뒤로가기, 제목·메타·canonical·sitemap/robots·대표 이미지 계획.
- 초기 HTML/색인·제품 렌더링 요구를 확인한 뒤 기존 스택 내 라우팅/사전 렌더 또는 필요한 대안을 근거로 선택. 현재는 기술 선택 미확정.
- 문의 실제 성공/실패/중복 제출·알림 흐름을 안전한 테스트로 확인. 사용자에게 보내는 검증 메일/실제 문의 전송은 승인된 테스트 대상으로만.
- 관리자 인증/권한/데이터 쓰기는 기존 보호를 유지. 변경 필요 시 별도 범위 제시.

산출물: 격리된 개발 브랜치/미리보기, 구현 diff, 기존 기능 회귀 검사, 마이그레이션/복귀 계획. 운영 main 병합/배포는 별도 승인.

## 단계 5 — 실제 고객 동선 QA와 콘텐츠 최종 확인
- 원단을 아는 바이어: 진입→원단군→검증된 상세→문의→테스트 접수 확인.
- 용도/샘플 방문자: 진입→용도 경로→조건 확인→문의.
- 모바일 메뉴/터치/키보드/포커스/모션 줄이기/이미지 대체/오류 상태/주소 직접 진입 검사.
- 이미지 최적화·지연 로딩·폰트·로딩 성능은 실제 화면에서 측정 후 개선. 수치 목표를 충족했다고 미리 주장하지 않음.
- SEO 색인 가능성·메타·기존 URL 영향·내부 링크, 개인정보/문의 동의 등 실제 수집 흐름 확인. 법적 내용 필요 시 최신 공식 근거 별도 검토.
- 측정은 제품/사용처 탐색·문의 시작·실제 성공을 구분. mailto 클릭을 문의 접수로 세지 않음. GA4/GSC 기존 수집 연결 및 중복 이벤트 확인.
- qa/design-review를 버전별 PASS/FAIL/미실행으로 작성. 디자인 효과/유효 문의 개선은 실제 운영 관찰 전 미검증.

산출물: 결함 수정 완료 목록·남은 위험·실사/문구 확인·릴리스 체크리스트·복귀 절차.
검토 지점 4: 실제 미리보기와 QA 결과를 보고 사용자 배포 승인.

## 단계 6 — 승인 후 공개와 실제 결과 확인
- 승인된 버전만 배포하고 도메인/주요 URL/이미지/문의/계측을 확인.
- 문제가 생기면 이전 버전으로 복귀할 수 있게 기록.
- 공개 직후 기술/문의 오류를 확인하고, 충분한 관찰 기간의 유입 출처·제품 접근·문의 품질을 비교. 이탈률 하나만으로 성공/실패 판단하지 않음.
- 추후 모니터링/정기 점검은 사용자가 요청하면 별도 자동화로 설정. 이번 계획만으로 자동 모니터를 생성하지 않음.

## 지금 바로 할 첫 작업
browser-04의 대표 구간 A/B 제작과 자산 등록부 확인. 사용자에게 먼저 신규 브랜드 설문을 하거나 Figma를 다시 연결하지 않는다. 생산 사이트 배포 준비보다 시각 방향을 실제로 보여주는 것이 우선이다.

## 관리
피드백 원문→.ai_history/feedback-log→해석/보완→특정 시안→QA→사용자 결정 순으로 추적. 시안은 덮어쓰지 않고 DRAFT/승인/반려 구분. 기간은 제품 실사/피드백·운영 조사에 따라 달라지므로 현재 고정 납기나 촬영 완료 날짜를 약속하지 않음.
